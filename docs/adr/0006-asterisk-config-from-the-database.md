# 0006 — Asterisk configuration from the database: realtime views for PJSIP, generated dialplan

- Status: accepted
- Date: 2026-11-25

## Context
CLAUDE.md: telephony configs are generated by Mira Core from the database; never hand-edit a running server. The study: "config written by Mira Core into the database (realtime) + templates". Task 1.1 had to choose how. Constraints: Mira's own tables (tenants, users, extensions, trunks) are the source of truth; new agents must work at once; Mira Cloud will run several Asterisk nodes behind Kamailio that must all see the same extensions; no secret may sit in clear text.

## Decision
1. **PJSIP endpoints, AORs and auths come from Asterisk realtime** (sorcery → `res_config_odbc` → PostgreSQL). They are **views** in schema `asterisk` over Mira's tables (`ps_endpoints`, `ps_aors`, `ps_auths`; migration 0002), not copies — nothing to sync, nothing can drift, no reload when an extension is added. Static `pjsip.conf` objects (transport, lab extensions) are read first, realtime second.
2. **The views encode the rules:** a row exists only for an enabled extension of an active tenant whose user (if any) is active, so disabling any of them takes the device off at its next request. Endpoints get the tenant's dialplan context (`t_<tenant uuid>`) and Asterisk's `tenantid`; media/NAT options match the `mira-endpoint` template (Kamailio + RTPengine in front).
3. **Passwords:** Mira stores only the SIP digest HA1; the view gives Asterisk 22 `auth_type=digest` + `password_digest=MD5:<ha1>` (`md5_cred` is deprecated in 22). The SIP password is generated by the API, shown once, never stored.
4. **Least privilege:** Asterisk logs in as role `asterisk` (password `ASTERISK_DB_PASSWORD` from install.sh, set by `mira-core ensure-db-roles` in `core-migrate`), `search_path=asterisk`, SELECT on the views only — no access to users, password hashes of staff, or any table.
5. **Dialplan is generated**, not realtime (realtime dialplan is slow and discouraged): Mira Core renders `generated/extensions_mira.conf` (one context per tenant: its extensions + an "unknown number" fallback) into a volume shared with Asterisk (read-only there), under a PostgreSQL advisory lock, written atomically and only when it changed, then reloads `pbx_config.so` over ARI (`PUT /asterisk/modules/{module}`). It is regenerated on every extension change and at Core startup; `mira-core render-config` does it by hand. Only database-validated identifiers reach the dialplan (no free text), so it cannot be injected.
6. **Trunks:** their outbound side (endpoint with `outbound_proxy` through Kamailio, AOR with the carrier address and transport) is in the views now. Inbound identification (through Kamailio, which sees the carrier's IP), outbound registration and encrypted credentials are task 1.2.

## Consequences
- Asterisk needs PostgreSQL to accept new calls from realtime endpoints; it starts after `core-migrate` and re-connects on its own. Contacts (registrations) stay in Asterisk's astdb.
- Changing an option for every endpoint = a new migration that redefines the views (CLAUDE.md: one migration per change).
- Every SIP request does a few indexed lookups on the views; a sorcery memory cache can be added if load tests (task 2.7) ask for it.
- Several Asterisk nodes (Mira Cloud) read the same views; only the generated dialplan must reach each node.
