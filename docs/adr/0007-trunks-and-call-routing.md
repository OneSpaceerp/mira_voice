# 0007: Trunks and call routing (carriers, registration, GSM gateways)

- Status: accepted
- Date: 2026-11-26
- Task: 1.2 (BUILD_GUIDE)

## Context
Mira needs three kinds of carrier connection:

- **Registration trunks.** Mira registers to the carrier (for example WE in Egypt) with a username and password.
- **IP-authenticated trunks.** The carrier trusts Mira's public IP.
- **GSM gateways.** A Yeastar or Dinstar box on the customer's LAN.

Mira also needs outbound routes (dialled pattern → trunks with failover) and inbound routes (DID → extension).

Constraints:
- All SIP enters through Kamailio, so Asterisk sees every request coming from 127.0.0.1 (ADR 0003).
- Mira must be able to read the carrier password back (to register and answer challenges), so it cannot only store a hash. It must still never sit in clear text in the database.
- Telephony config is generated, never hand-edited (CLAUDE.md, ADR 0006).

## Decision

### 1. Trunks are generated into `generated/pjsip_mira.conf`, not realtime views
Migration 0003 drops the trunk rows that 0002 put in the views. A trunk needs objects the views cannot express:
- `identify` by header
- outbound `auth` with a decrypted password
- `registration`

Mira Core renders all trunk objects into this file and reloads `res_pjsip` and `res_pjsip_outbound_registration` over ARI when the file changes. The file is `0640 mira:mira-config` (gid 2701, shared by the Core and Asterisk images), because it holds carrier passwords.

### 2. Carrier passwords are encrypted at rest
- They are stored with Fernet (AES-128-CBC + HMAC-SHA256, `cryptography`), using `MIRA_DATA_KEY` from `/opt/mira/.env`.
- `install.sh` generates the key and keeps it on upgrades.
- `MIRA_DATA_KEY` may hold several comma-separated keys, newest first (MultiFernet), so the key can be rotated.
- The API never returns a password. It only returns `has_password`.

### 3. Inbound identification by Kamailio
- Kamailio dispatcher **set 2** is generated by Mira Core into `kamailio-generated/dispatcher.list`. It lists each carrier's signalling IPs: `inbound_ips`, plus `host` when `host` is a literal IP.
- Each row has the attribute `trunk=trunk_<id>` and flag 32 (never pinged).
- On every request that does not come from Asterisk, Kamailio removes any `X-Mira-Trunk` header. When the source IP is in set 2 (`ds_is_from_list(2, 3)`: IP only, any port or transport), Kamailio adds `X-Mira-Trunk: trunk_<id>` itself.
- Asterisk's `identify` uses `match_header` on that header.
- `endpoint_identifier_order = ip,auth_username,username`. A phone cannot pose as a carrier: its header is removed, and a stranger's forged header is removed too (tested).
- Carrier IPs skip the pike flood limit.
- A carrier IP can belong to only one trunk (the API returns 409, and the generator refuses duplicates).
- A carrier only reaches its tenant's inbound context: incoming calls can ring extensions but can never dial out.

### 4. Registration trunks
- Asterisk registers through Kamailio (`outbound_proxy`). Kamailio rewrites the REGISTER `Contact` from `127.0.0.1:5080` to the public address (`:5061;transport=tls` for TLS carriers).
- The carrier then calls `sip:trunk_<id>@<public IP>`. Kamailio replaces that R-URI user with the To user (the DID) before passing the call on.
- The registrar's IP must be in the trunk's carrier IPs. It is added automatically when `host` is an IP; otherwise the runbook says to enter it.

### 5. GSM gateways
- The gateway registers to Mira like a phone. Mira is the registrar.
- Mira generates the account: username `trunk_<id>`, realm `mira`, and a 144-bit password shown once. Only the HA1 is kept (as for extensions).
- The gateway is not in the carrier list. It is identified by its digest username.

### 6. Outbound routes
- Each route has an Asterisk pattern (without `_`), strip, prepend and caller ID, plus up to 10 trunks in order.
- The generated dialplan calls a static `[mira-outbound]` subroutine (in `extensions.conf`) with the number and `(trunk, caller ID)` pairs.
- The next trunk is tried only on `CHANUNAVAIL` or `CONGESTION`, never after BUSY or NOANSWER (that would ring the callee twice).
- Caller ID is taken from the route, then the trunk, then the caller's own number.
- If every trunk fails, the call is hung up with cause 34 (no circuit available).
- A dead carrier is detected by Asterisk's qualify (OPTIONS every 60 s; unreachable after 3 s), so failover is immediate.

### 7. Inbound routes
- An inbound route is a DID (or `*` for any number), on one trunk or on all trunks of the tenant, ringing an extension of that tenant.
- Each trunk has its own context `t_<tenant>_in_<trunk>`, which includes the tenant-wide `t_<tenant>_in`. A trunk-specific route therefore beats a tenant-wide one.
- Unknown numbers get the "invalid number" prompt.
- The destination must be an existing extension when the route is created. Later IVR, queue and ring-group destinations come with tasks 1.3–1.5.

### 8. Reloads
- Kamailio reloads its list through JSON-RPC over HTTP on `127.0.0.1:8095` (`dispatcher.reload`). The request must carry `X-Mira-Token` (`KAMAILIO_RPC_TOKEN` from `.env`), and loopback is the only source accepted.
- Kamailio refuses a reload that arrives too soon after the previous one. On 6.1.6 the answer is **HTTP 500 "Ongoing reload"**, not a JSON-RPC error.
  - `reload_delta` is set to 1 s. The docs keep 0 for test environments only.
  - Mira Core retries a refused reload up to 5 times, 1.2 s apart. Without this, an admin creating two trunks in quick succession left the second one out of Kamailio (seen in testing).
  - A 4xx answer (wrong token) is not retried.
- `core-migrate` runs `render-config` before Asterisk and Kamailio start, so they find their files at first boot.

### 9. Asterisk details found in testing
- In Asterisk 22, a `registration` that names an `endpoint` is refused unless line support is on. Mira's registrations name no endpoint, because carrier calls are matched by the header (decision 3).
- Deleting a registration trunk makes Asterisk de-register it (`Expires: 0`) and stop. While the carrier does not answer, the de-REGISTER is retransmitted for about 30 s.

## Consequences
- Losing `MIRA_DATA_KEY` loses the stored carrier passwords; they must then be entered again. The key lives in `.env`, which the backup must include (task 2.x backup).
- Kamailio trusts the source IP of a carrier. The trunk's carrier IP list must be exact: a wrong IP lets that address call into the tenant's inbound routes. It still can never call out.
- Failover depends on Asterisk's OPTIONS keepalive (every 60 s). A carrier that never answers OPTIONS is marked unreachable, and calls to it fail. Most carriers answer; a per-trunk "no keepalive" switch will be added when one does not (it then fails over only on 503 and congestion).
- `max_channels` is stored but not yet enforced. The per-tenant call and spend limits arrive with the anti-fraud task (CLAUDE.md rule 5).
- Asterisk's realm for its own digest challenges stays `mira`. A gateway must be configured with that realm (or no realm).
